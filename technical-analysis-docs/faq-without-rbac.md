# 无 RBAC 模式常见问题

> 本文收集无 `RBAC` 模式下最容易产生误解的问题，重点从“实际使用体验”出发回答，而不是复述后端实现。

---

## 1. 什么叫“无 RBAC 模式”？

它的意思不是“谁都可以做任何事”，而是：

- 系统不再按角色做一套复杂的权限分层
- 主要依赖“当前用户是谁”以及“资源归谁所有”来控制访问

从用户角度看，最重要的变化是：

- 你的私有 Skill 仍然只属于你
- 系统额外开放了 `public` Skill 供所有用户使用

---

## 2. 我能看到哪些 Skill？

通常你能看到：

- 你自己的私有 Skill
- 你自己创建的 `reference`
- 你自己创建的 `clone`
- 系统提供的 `public` Skill

你通常看不到：

- 别人的私有 Skill
- 别人的 `reference`
- 别人的 `clone`

---

## 3. 为什么我能看到 `public` Skill，却不能像自己的 Skill 一样修改它？

因为 `public` Skill 的定位是“系统公共能力库”，不是“公共可写工作区”。

你能：

- 浏览
- 查看详情
- 查看文件和版本
- 创建 `reference`
- 创建 `clone`

你不能：

- 修改公共 Skill 本体
- 删除公共 Skill 本体
- 把它当成自己拥有的 Skill 去维护

---

## 4. 为什么我能看到某个 `public` Skill，却不能直接执行或下载它？

因为 `public` Skill 的定位是“可检查的公共来源”，不是“可直接消费的工作空间 Skill”。

在无 `RBAC` 模式下：

- 很多可见 Skill 可以被查看
- 但真正的执行和下载只允许落在自己空间里的 Skill 上

最典型的情况就是：

- `public` Skill 可见、可查看
- 但默认不能直接执行本体，也不能直接下载本体
- 如果你想运行或下载，应该先创建 `reference` 或 `clone`

---

## 5. `reference` 和 `clone` 到底怎么选？

最简单的判断方式：

- 想轻量接入，不准备深改：选 `reference`
- 想拿来改代码、长期维护：选 `clone`

你可以把它们理解成：

- `reference`：把公共 Skill 收到自己名下，但不复制文件
- `clone`：把公共 Skill 真正复制成自己的副本

---

## 6. 为什么我已经把公共 Skill 加到自己的列表里了，却还是觉得它不像“完全属于我”？

因为你加进去的不一定是独立副本。

如果你创建的是 `reference`：

- 它在列表里属于你的视角
- 但内容来源仍然依赖公共 Skill

如果你想得到一个完全独立、可自由维护的版本，应该创建 `clone`。

---

## 7. 我的私有 Skill 会不会被其他用户看到？

不会，默认不会。

无 `RBAC` 模式下的核心前提之一就是：

**私有 Skill 仍按 owner 隔离。**

只要它是你的私有 Skill，别人通常既看不到，也调用不了。

---

## 8. “给自己的客户端提供服务”到底是什么意思？

它的意思是：

- 你的客户端用你的 token 连接系统
- 客户端以你的身份访问系统
- 客户端发现并调用“你可见的 Skill”

这里的“自己的客户端”可以理解成：

- 你自己配置的 MCP 客户端
- 你自己的自动化脚本
- 你自己的 Agent 运行环境

它不等于“平台上所有用户都能调用你的私有 Skill”。

---

## 9. 为什么我创建了 Token，还是什么都没有发生？

因为 Token 只是“访问凭证”，不是 Skill 本身。

你还需要同时满足两件事：

- 账号下已经有可用 Skill
- 你的客户端已经正确使用这个 Token 去接入系统

如果没有可用 Skill，客户端就算接入成功，也不会有可调用的内容。

---

## 10. 为什么我刚注册时更建议先去 `Public Skills`，而不是马上自己上传？

因为大多数新用户一开始并不缺“上传能力”，而是缺“对系统结构的理解”。

先看 `Public Skills` 有三个好处：

- 更快知道 Skill 在系统里长什么样
- 更容易判断 `reference` 和 `clone` 的区别
- 更快用最短路径跑通整个流程

---

## 11. 我什么时候应该从 `reference` 切换到 `clone`？

当你开始出现下面这些需求时，就应该认真考虑 `clone`：

- 想改代码
- 想调整描述或结构
- 想独立维护版本
- 不希望继续依赖公共来源

如果只是“拿来就用”，`reference` 更轻。

---

## 12. 无 RBAC 模式适合团队共享吗？

不适合作为主要共享模型。

更准确地说，它的设计重心不是“多人协作”，而是：

- 个人私有空间
- 系统公共能力库

如果你的主要诉求是团队级共享、组织级管理、精细角色权限，无 `RBAC` 不是最贴切的模式。

---

## 13. 为什么有些管理页面或接口看起来存在，但我用不了？

因为“存在”不等于“当前模式下对你开放”。

在无 `RBAC` 模式下：

- 某些管理类页面或接口不是普通用户主路径
- 某些功能受前端开关或后端开关控制
- 某些路由只是代码层面存在，不代表它是当前模式下的推荐入口

最重要的是先聚焦主路径：

- `Skills`
- `Public Skills`
- `Tokens`
- `Profile`
- `Security`

---

## 14. 如果我只想最快跑通一遍系统，最推荐的顺序是什么？

建议顺序如下：

1. 登录
2. 打开 `Public Skills`
3. 挑一个公共 Skill，先创建 `reference`
4. 回到 `Skills` 页面确认它已经在你的列表里
5. 创建 API Token
6. 在自己的客户端里接入并调用

这通常是理解成本最低的一条路径。

---

## 15. 如果我想长期维护自己的能力库，最推荐的顺序是什么？

建议顺序如下：

1. 先浏览 `Public Skills`，看是否已有合适起点
2. 如果有，优先 `clone`
3. 如果没有，直接创建自己的私有 Skill
4. 持续在 `Skills` 和 Skill 详情页里维护
5. 用 `Tokens` 给自己的客户端接入

这条路径更适合长期使用，而不是一次性试用。
