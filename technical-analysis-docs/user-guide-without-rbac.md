# 无 RBAC 模式用户操作手册

> 这是一份面向最终使用者的说明文档。它不关注后端实现细节，而是回答一个更实际的问题：**在不启用 RBAC 的情况下，我登录系统后到底能做什么，应该怎么做。**

---

## 适用范围

本文适用于以下使用场景：

- 系统运行在 `ENABLE_RBAC=false`
- 用户以个人身份使用系统
- 目标是管理自己的私有 Skill，并通过自己的客户端调用它们

如果你想了解更偏技术和权限边界的说明，可以继续阅读：

- [不开启 RBAC 时系统功能清单](./feature-list-without-rbac.md)
- [无 RBAC 模式下的权限模型说明](./permission-model-without-rbac.md)

---

## 一句话理解这个模式

无 `RBAC` 模式下，系统最适合被理解成：

**一个以“个人私有 Skill 空间”为核心，同时附带“系统公共 Skill 库”的平台。**

你可以：

- 管理自己的 Skill
- 使用系统提供的 `public` Skill
- 把 `public` Skill 变成自己的 `reference` 或 `clone`
- 用自己的 token / MCP 客户端调用自己可见的 Skill

你不能：

- 修改别人的私有 Skill
- 看到别人的私有 Skill
- 把自己的私有 Skill自动开放给其他用户

## 新用户第一次使用时的推荐路径

如果你是第一次登录，建议按下面的顺序操作。

### 第一步：先确认自己能进入控制台

登录成功后，你通常会进入控制台首页或仪表盘。  
这一步只需要确认三件事：

- 账号登录正常
- 能进入 `Skills` 页面
- 能进入 `Public Skills` 页面

只要这三件事正常，就说明你的账号已经可以使用系统的主要能力。

### 第二步：先浏览 Public Skills

如果你还没有自己的 Skill，最好的起点通常不是马上从零上传，而是先去 `Public Skills` 页面看看系统已经提供了什么。

这样做的好处是：

- 可以快速理解 Skill 在系统里的组织方式
- 可以直接试用系统预置能力
- 可以判断自己更适合创建 `reference` 还是 `clone`

如果你只是想先用起来，通常优先选 `reference`。  
如果你知道后续一定要改代码或长期维护，通常优先选 `clone`。

### 第三步：创建或上传自己的 Skill

如果你已经有自己的 Skill 包，或者准备从头维护一套自己的 Skill，就进入 `Skills` 页面进行创建和上传。

这一类 Skill 的特点是：

- 完全归你自己所有
- 后续可以由你自己继续上传新版本、修改、停用或删除
- 可以被你自己的客户端发现和调用

### 第四步：创建 API Token

如果你的目标不仅是“在网页里管理 Skill”，而是“让自己的 AI 客户端实际调用 Skill”，下一步就应该去 `Tokens` 页面创建 API Token。

这个 Token 的用途是：

- 给 MCP 客户端或其他自动化客户端做认证
- 让客户端以“你的身份”访问系统
- 发现并调用“你可见的 Skill”

这里最关键的一点是：

**客户端看到的是“你可见的 Skill 集合”，不是整个平台的全部 Skill。**

### 第五步：在自己的客户端中接入

接入后，你的客户端通常能发现：

- 你自己的私有 Skill
- 你自己创建的 `reference`
- 你自己创建的 `clone`
- 系统的 `public` Skill

但它看不到别人的私有 Skill。

## 你会接触到的几类 Skill

为了减少误解，建议把系统中的 Skill 先分成四类来理解。

### 1. 自己的私有 Skill

这是你最核心的工作区。

特点：

- 由你自己创建
- 由你自己维护
- 只有你自己和你的客户端能看到和调用
- 后续可以继续上传、修改、删除、停用

适合：

- 你自己写的专用工具
- 只服务于你个人工作流的 Agent 能力
- 不希望别人看到的业务逻辑

### 2. Public Skill

这是系统提供的公共能力库。

特点：

- 系统预置
- 所有用户都能浏览和使用
- 但普通用户不能直接改它

适合：

- 先体验系统能力
- 拿来做起点
- 用作通用模板或公共底座

### 3. Reference Skill

你可以把它理解成“把一个公共 Skill 收到自己名下，但不复制文件”的方式。

特点：

- 记录归你所有
- 内容仍跟着源公共 Skill
- 更轻量
- 更适合先接入再使用

适合：

- 你只想用，不准备大改
- 希望尽量少占自己的空间
- 希望保持和公共版本接近

### 4. Clone Skill

你可以把它理解成“从公共 Skill 复制出一份真正属于自己的副本”。

特点：

- 文件副本归你所有
- 后续可以像普通私有 Skill 一样维护
- 更适合长期演化

适合：

- 你准备基于公共 Skill 做二次开发
- 你需要独立版本节奏
- 你希望后续完全自己掌控

## 常见任务怎么做

下面按用户最常见的目标来写。

### 任务 1：我想快速开始，但暂时没有自己的 Skill

建议做法：

1. 打开 `Public Skills`
2. 浏览系统预置 Skill
3. 找到合适的 Skill 后，优先尝试 `Add Reference`
4. 回到 `Skills` 页面确认它已经出现在你的列表里
5. 再通过自己的客户端调用

这条路径最适合“先跑通，再考虑定制”。

### 任务 2：我想完全拥有一份可修改的副本

建议做法：

1. 打开 `Public Skills`
2. 选中目标 Skill
3. 使用 `Clone`
4. 回到 `Skills` 页面查看新副本
5. 后续在该 Skill 详情页继续编辑、上传、维护

这条路径最适合“公共 Skill 只是起点，后面我要自己维护”。

### 任务 3：我已经有自己的 Skill 包，想上传到系统

建议做法：

1. 进入 `Skills` 或 `Create Skill`
2. 创建一条新的 Skill 记录，或直接通过上传入口创建
3. 上传 ZIP 或相关文件
4. 在 Skill 详情页确认版本、文件和状态
5. 用自己的客户端接入并执行

这条路径最适合已经有现成 Skill 工程的人。

### 任务 4：我想让自己的客户端调用 Skill

建议做法：

1. 去 `Tokens` 页面创建 API Token
2. 在自己的客户端或 MCP 配置里使用这个 Token
3. 让客户端以你的身份连接系统
4. 在客户端里发现并调用你可见的 Skill

这里的重点不是“把 Skill 分享出去”，而是“让自己的客户端以自己的身份来使用自己的 Skill”。

## 下载、执行、修改这三件事不要混为一谈

系统里最容易让人误解的，就是这三件事看起来都像“我可以操作这个 Skill”，但实际上不是一回事。

### 你能执行，不代表你能修改

典型例子：

- 你能执行 `public` Skill
- 但你不能修改 `public` Skill 本体

### 你能看到，不代表你能下载

典型例子：

- 你能在 `Public Skills` 里看到公共 Skill
- 但无 `RBAC` 模式下，`public` Skill 默认不能直接下载本体

### 你能拥有一条记录，不代表它就是独立副本

典型例子：

- `reference` 在你的 Skill 列表里
- 但它本质上仍然是指向公共 Skill 的引用

如果你发现自己开始混淆这几件事，最简单的判断方法是：

- 想改代码：优先 `clone`
- 想轻量接入：优先 `reference`
- 想完全私有维护：创建自己的 `private` Skill

---

## 用户最需要知道的边界

### 1. 别人看不到你的私有 Skill

只要是你自己的私有 Skill，它就不会自动暴露给其他用户。

### 2. 你的客户端可以用你的私有 Skill

只要客户端使用的是你的 token，并以你的身份接入，它就可以发现和调用你可见的 Skill。

### 3. Public Skill 不是公共可写空间

它是公共可见、公共可用，但不是公共可编辑。

### 4. 无 RBAC 不是多人协作共享模式

它更像“个人私有空间 + 公共能力库”，而不是“按组织共享的协作平台”。

---

## 一条最实用的建议

如果你只是想尽快跑起来，建议采用下面这个顺序：

1. 先看 `Public Skills`
2. 先用 `reference` 跑通
3. 确认确实要改，再改用 `clone`
4. 只有在明确需要完全自建时，再从零上传自己的 Skill

这样通常能最快建立对系统的正确理解，也最不容易在“权限”和“资源归属”上产生误解。
