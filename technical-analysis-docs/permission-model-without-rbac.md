# 无 RBAC 模式下的权限模型说明

> 本文聚焦 `ENABLE_RBAC=false` 时，系统中“谁能看到什么、谁能修改什么、谁能执行什么、谁能下载什么”。目标是把容易混淆的几个概念拆开说明，避免把“可见”“可管理”“可执行”“可下载”混成一句话。

---

## 一句话结论

在不开启 `RBAC` 的情况下，系统不是“所有已登录用户都能互相操作彼此的 Skill”，而是：

- 用户始终只能管理自己名下的 Skill。
- 系统会额外开放 `public` Skill 的浏览和使用能力。
- 用户自己的私有 Skill 可以被**自己的客户端**发现和调用。
- 用户自己的私有 Skill 不会自动暴露给其他用户。

如果要用一句更准确的话描述当前行为，可以写成：

> 在 `RBAC` 关闭时，用户默认只能管理自己名下的 Skill；系统额外开放 `public` Skill 的浏览、引用、克隆和执行。只要用户私有空间里存在 Skill，这些 Skill 就可以通过该用户自己的 token / MCP 客户端被其自己的客户端发现并调用，但不会对其他用户开放。

---

## 先区分四个概念

在阅读后端实现或讨论产品行为时，建议先把下面四件事分开：

| 概念 | 问题本质 | 典型接口/场景 |
|------|----------|---------------|
| 可见 | 我能不能在列表里看到它，或按 ID 访问到它 | 技能列表、技能详情、MCP `skill://list` |
| 可管理 | 我能不能修改、上传、重命名、停用、删除 | 更新 Skill、上传文件、删除 Skill |
| 可执行 | 我的客户端能不能调用它来运行 | MCP `execute_skill` |
| 可下载 | 我能不能把 Skill 文件打包导出 | `/api/v1/skills/download` |

很多误解都来自一句模糊的话，例如“用户可以操作 public 和自己的私有空间”。  
这句话最大的问题是把“能看”和“能改”混在了一起。

---

## 核心规则

### 1. 认证通过不等于可以操作所有 Skill

当 `RBAC` 关闭时，`require_permission(...)` 这类权限依赖基本会放开，但真正的资源边界并没有消失。后端仍然通过下面两层约束控制访问：

- **可见性判断**：当前用户是否“看得见”这个 Skill
- **所有权判断**：当前用户是否是这个 Skill 的 owner

这意味着系统并没有退化成“登录后全员共享一切”，而是退化成更简单的“身份认证 + 资源所有权”模型。

### 2. 无 RBAC 时，可见范围 = 自己的 Skill + public Skill

无 `RBAC` 时，后端列出可见 Skill 的查询会把两类资源拼在一起：

- 自己名下的 Skill
- `visibility = public` 的 Skill

这也是为什么用户在列表里既能看到自己的私有 Skill，也能看到系统预置的公共 Skill。

### 3. 管理操作仍然只允许 owner 执行

即使某个 Skill “可见”，也不代表它“可修改”。  
涉及以下操作时，后端仍会校验 owner：

- 修改元数据
- 上传文件
- 删除
- 停用 / 启用
- 重命名

换句话说：

- 你能看到 `public` Skill
- 你甚至能执行它
- 但你不能把它当成“你的 Skill”去修改

### 4. 下载权限比“可见”更严格

无 `RBAC` 时，下载接口不是按“可见”判断，而是按“是否属于自己”判断。  
因此：

- 自己的私有 Skill 可以下载
- 自己创建的 `reference` / `clone` 可以下载
- `public` Skill 本体不能直接下载

这也是很多人第一次读代码时最容易忽略的一点：  
**`public` Skill 可见、可执行，但默认不可直接下载。**

### 5. MCP 客户端看到的是“当前用户可见的 Skill”

MCP 侧不是直接把整个文件系统暴露给客户端，而是会先根据当前用户身份过滤 Skill 列表，再允许客户端去读详情或执行。

因此在无 `RBAC` 模式下，一个用户自己的客户端通常能看到：

- 自己的私有 Skill
- 系统的 `public` Skill
- 自己创建的 `reference` Skill
- 自己创建的 `clone` Skill

但看不到：

- 别人的私有 Skill
- 别人的 `reference`
- 别人的 `clone`

## 权限总表

下面这张表是无 `RBAC` 模式下最实用的一张速查表。

| 资源类型 | 谁能看到 | 谁能修改 | 谁能执行 | 谁能下载 |
|------|------|------|------|------|
| 自己的 `private` Skill | 自己 | 自己 | 自己 | 自己 |
| 别人的 `private` Skill | 不能 | 不能 | 不能 | 不能 |
| `public` Skill | 所有用户 | 普通用户不能改 | 所有用户可执行 | 不能直接下载 |
| 自己基于 `public` 创建的 `reference` | 自己 | 只能做引用相关操作，不能改内容本体 | 自己 | 自己可下载 |
| 自己基于 `public` 创建的 `clone` | 自己 | 自己 | 自己 | 自己 |

如果要再简化成一句口语化的判断：

- `private` 看 owner
- `public` 看 everyone
- “改不改得了”看 owner
- “下不下得了”在无 `RBAC` 时也看 owner

## 几类 Skill 分开理解

### 1. 普通私有 Skill

这是最符合直觉的一类：

- 用户自己创建
- 用户自己上传文件
- 用户自己修改
- 用户自己的客户端发现并执行

它的服务对象是“这个用户自己的客户端”，而不是平台里所有用户。

### 2. Public Skill

`public` Skill 的定位是“系统预置、供所有用户使用的只读基础能力”。

用户对它通常可以做的事：

- 浏览
- 查看详情
- 执行
- 基于它创建 `reference`
- 基于它创建 `clone`

用户对它不能做的事：

- 上传文件
- 改描述、标签、代码内容
- 删除
- 停用
- 在无 `RBAC` 模式下直接下载本体

因此，`public` 更像“共享只读模板库”，而不是“大家共用的可写工作区”。

### 3. Reference Skill

`reference` 的关键点不是“复制”，而是“指向”。

它的特点是：

- 记录属于当前用户
- 文件内容实际来自源 `public` Skill
- 在当前用户视角下，它是“我名下的一条可用 Skill 记录”
- 但它本身是只读引用，不适合当成独立副本去改代码

它适合“先接入再用”的场景，不适合“我要基于它深改”。

### 4. Clone Skill

`clone` 是真正意义上的独立副本。

它的特点是：

- 创建完成后归当前用户所有
- 文件已经复制到用户自己的空间
- 后续可以独立修改、上传、重命名、删除
- 行为上更接近普通私有 Skill

它适合“拿公共 Skill 当起点，但后续要自己维护演化”的场景。

## 典型用户旅程

下面用一个具体例子把整个流程串起来。

### 场景：用户 A 注册后开始使用系统

用户 A 登录后，会看到两类 Skill：

- 自己名下的 Skill
- 系统提供的 `public` Skill

此时如果 A 上传一个自己的 Skill，例如 `my-report-skill`：

- A 的 Web 控制台可以看到它
- A 的 MCP 客户端可以发现它
- A 的 MCP 客户端可以执行它
- A 可以继续上传、改名、删除它
- 用户 B 看不到它，也执行不了它

如果 A 看到一个系统的 `public` Skill，例如 `starter-data-cleaner`：

- A 可以直接执行它
- A 可以基于它创建一个 `reference`
- A 也可以基于它创建一个 `clone`
- A 不能直接修改这个 `public` Skill 本体

如果 A 创建的是 `reference`：

- A 以后还是可以从自己的客户端看到这条 Skill
- 这条记录归 A 所有
- 但底层内容仍来自源公共 Skill

如果 A 创建的是 `clone`：

- A 会得到一个真正属于自己的副本
- 后续可以像普通私有 Skill 一样维护

## 常见误解

### 误解 1：RBAC 关闭后，所有用户都能互相看到对方的 Skill

不对。  
无 `RBAC` 并不等于没有隔离。私有 Skill 仍按 owner 隔离，别人看不到也调用不了。

### 误解 2：既然 public Skill 可见，那就应该也能直接下载

不对。  
当前实现里，下载在无 `RBAC` 时单独收紧为“只能下载自己拥有的 Skill”。这比“可见即可下载”更严格。

### 误解 3：用户自己的私有 Skill 一旦被 MCP 发现，就等于对平台所有人开放

不对。  
MCP 的可见范围是“当前用户可见的 Skill 集合”，不是“系统全局 Skill 文件夹”。

### 误解 4：Reference 就是一个普通私有 Skill

不完全对。  
它在“归属关系”上属于用户，但在“内容来源”上仍依赖源公共 Skill，本质是只读引用而不是独立副本。

## 面向产品和文档的推荐表述

如果要在 PR、设计文档、需求说明或者用户手册里描述这一行为，建议优先使用下面这种表述：

> 在 `RBAC` 关闭时，用户默认只能管理自己名下的 Skill。系统会额外开放 `public` Skill 的浏览、引用、克隆和执行能力。用户自己的私有 Skill 可以通过该用户自己的 token / MCP 客户端被其自己的客户端发现并调用，但不会自动对其他用户开放。

不建议使用下面这种容易产生误解的说法：

> 用户可以操作自己的私有空间和 public 空间。

这句话的问题是“操作”过于含糊，没有区分：

- 能看
- 能改
- 能执行
- 能下载

而这四件事在当前实现里并不等价。

---

## 结论

无 `RBAC` 模式的本质，不是“彻底开放”，而是“简化后的个人私有空间模型”：

- 私有空间仍然严格按 owner 隔离
- `public` 空间提供只读共享能力
- 客户端可发现的是“当前用户可见的 Skill”
- 可见不等于可改
- 可见也不等于可下载

如果从产品视角来理解，这个模式最适合的定位是：

**一个以个人私有空间为主、辅以系统公共能力库的 Skill 平台。**
